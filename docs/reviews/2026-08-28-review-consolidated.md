### NEW IN PASS 2

Seven pass-2 findings describe defects pass 1 did not independently reach:

1. **P2-2 — unconfined run paths (CRITICAL, CONFIRMED).** `--run-id` and `--resume` flow directly into `Path("scorecards") / rid` (`gauntlet/cli.py:244-248,274-275`), and `RunPaths.ensure()` creates that resolved directory before raw ledgers are appended (`gauntlet/runner.py:32-49`). A value containing `..` can therefore place private checkpoint files in the tracked tree. The `--out` portion is not itself path traversal—the destination is explicitly user-selected—but it shares the privacy problem when a non-shared card is written into a publishable location.
2. **P2-9 — judge-call failures escape the typed case outcome (HIGH, CONFIRMED).** The subject call is inside the `GauntletError` handler, but `score_with_judge()` is called afterward and its `client.chat()` is not caught (`gauntlet/runner.py:202-235`; `gauntlet/scoring/judge.py:47-56`).
3. **P2-13 — explicit model-load failure is ignored (HIGH, CONFIRMED).** `vram.load()` returns a success boolean (`gauntlet/vram.py:214-236`), but `execute_plan()` discards it and continues to ping and infer (`gauntlet/runner.py:332-353`).
4. **P2-14 — judge models bypass exclusive-VRAM load accounting (HIGH, PLAUSIBLE).** The runner explicitly loads only the subject model, then sends judge requests through the same serving target without a corresponding load/context/unload transition (`gauntlet/runner.py:225-235,332-382`). The missing bookkeeping is clear; the exact failure mode depends on the server's JIT-load behavior.
5. **P2-17 — degenerate embeddings and unconstrained `k` inflate recall (MEDIUM, CONFIRMED).** Stable tie ordering gives constant vectors 0.5 on the seeded `[0,2]` relevance set, while the CLI accepts `k` at least as large as the three-document corpus, making every ranking score 1.0 (`gauntlet/batteries/embed.py:21-32,35-59`; `gauntlet/cli.py:369-424`; `cases/embed/corpus.yaml:1-8`).
6. **P2-20 — truncation attribution omits non-code scorers (MEDIUM, PLAUSIBLE).** The reattribution allowlist contains only two code-exec failure modes, so a truncated exact/regex/schema response remains a scored zero (`gauntlet/runner.py:52-79,223-238`; `tests/test_truncation_attribution.py:79-85`).
7. **P2-22 — parent death can orphan a sandbox child and scratch directory (MEDIUM, PLAUSIBLE).** The child starts in a new session/process group, but tree termination is invoked only after the parent observes its own timeout (`gauntlet/scoring/execute.py:214-255,316-340`). A hard-killed parent cannot run that cleanup.

## Disputed or unclear

- **Whether `busy` must react to a config edit made after a run starts (pass 1 H-4 subclaim) is unclear.** The code snapshots config once (`gauntlet/cli.py:268-293`; `gauntlet/runner.py:284-286`), but the repository guidance does not state that `busy` is a live kill switch. An explicit product decision plus an end-to-end test that flips `busy` between profiles would settle whether polling/reload is required. The independently confirmed depth/embed bypass and fail-open mapping defects do not depend on this question.
- **The exact live consequence of judge JIT loading (P2-14) is server-dependent.** Code inspection proves the missing load/context/unload bookkeeping, but a synchronized LM Studio test observing resident models before, during, and after a judge call would settle whether the server co-resides, evicts, or rejects the judge and how subsequent subject cases are affected.
- **Cross-platform persistence after hard parent death (P2-22) was not reproduced.** A subprocess test that kills the parent externally and then checks the child tree and scratch directory on both Windows and Linux would settle the platform-specific extent. The current cleanup is demonstrably limited to the parent-observed timeout path.
